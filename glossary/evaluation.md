# 研究证据与评测方法词典

技术报告不能只转述项目自述或给出一个指标。要先说明主张的具体对象、评测设置、对照条件和证据级别，再讨论结果能支持多强的结论。

### 官方 Trending

GitHub Trending 是发现近期受关注仓库的入口，不是研究质量排名，也不等于一周新增 Star 排名。语言筛选、时间窗口、页面规则和采样时间都会影响观察。报告应区分“本周榜单信号”与“长期技术价值”，不能把研究入口清单冒充榜单。

### 周增 Star 与跨期比较

周增 Star 应来自同一数据源、同一时区和明确周初/周末时间点的快照差值。采样时间不一致、页面缓存、删除账号或抓取失败都可能影响数字。没有同期快照时应只报告当前可见值或不报告趋势，不编造增长率。

### 证据等级

可将证据按主张区分为：项目方陈述、可运行 demo、可复现实验、匹配条件的对照/消融、独立复现、形式化检查、真实环境验证及同行评议。不同领域所需证据不同：软件基准需环境和代码，数学需要证明检查与审查，机器人需要任务和硬件条件。等级不是简单单向排名，而是“什么证据验证了什么主张”。

### 复现

根据公开代码、数据、依赖和配置重新得到结果。复现至少要锁定代码 commit、数据版本、模型权重、运行环境、随机种子、参数与硬件；只跑通 demo 不等于复现论文结论。若结果存在随机性，应报告多次运行分布而非单次最好分数。

### 基准与数据切分

基准由任务、数据、指标和运行规则共同定义。测试数据若与训练集存在重复或近重复、切分泄漏或提示模板过度贴近训练分布，分数可能高估泛化。比较前应确认数据版本、切分策略、提示/工具权限、模型版本和评分程序一致。

### 消融实验

移除、替换或关闭某一组件，并保持其他条件尽可能一致，以估计它对结果的贡献。缺少消融时，无法清楚归因性能提升究竟来自架构、数据、训练预算还是额外工具。消融结论也只适用于所测试的配置，不一定能外推到不同规模或负载。

### 因果归因

观察到 A 与较好结果同时出现，不表示 A 导致结果。要支持因果主张，应控制其他变量、使用合理基线和重复实验，避免同时更改数据、模型、硬件与参数。热门度、Star 数或演示效果不能证明技术设计带来了性能提升。

### 性能报告口径

LLM 需报告模型/量化、硬件、输入与输出长度、并发、TTFT、每 token 延迟、吞吐和输出质量；Agent 需报告任务成功率、工具误用、人工介入、成本和副作用；机器人需报告本体、动作空间、试验次数、成功定义和闭环条件。不同口径的数据不应直接比较。

### 基准污染

训练或开发过程可能间接接触测试题及答案，令评测结果不能反映真正泛化。污染不限于逐字重复，也包括改写、同一模板或公开题解。要报告来源、去重策略、时间切分和留出测试集的构建方式。

### 研究主张与独立验证

项目方文档适合确认项目声称做了什么，不能自动视为独立验证。应标注官方声明、第三方实验、独立复现、形式化验证和分析推断；遇到撤回、修订或数据不全时，要保留不确定性。

### 技术影响判断

影响判断应沿机制链推导：设计改变了什么资源/信息/决策环节，为什么可能改善结果，付出的代价是什么，以及哪些证据会改变判断。应把“已发生的影响”与“潜在影响”分开，避免将技术可行性写成行业必然趋势。

## 阅读建议

每个重要结论都要能回答：主张是什么、在何种条件下成立、由谁提供证据、可否独立复核、尚有哪些替代解释？没有答案时，应降低结论强度而不是补齐想象中的数字。
