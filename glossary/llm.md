# LLM 与推理系统词典

本词典重点解释模型服务的运行机制、瓶颈和性能口径。阅读推理框架时，先区分模型计算、显存管理、请求调度和网络服务四层；不同优化作用于不同瓶颈，不能互相替代。

### Transformer

以注意力层和前馈网络为核心的序列建模架构。自注意力根据当前 token 与上下文 token 的关系聚合信息，前馈层完成逐位置变换。它提供上下文条件生成能力，但不内置事实核验或可靠规划机制；模型输出是否正确仍取决于训练、上下文和外部验证。

### 自回归生成

模型按 token 顺序反复预测下一个 token，直到停止条件满足。生成阶段每一步依赖先前 token，因此历史表示缓存、批处理和停止逻辑会影响速度与资源消耗。应分别测 prefill（处理输入上下文）和 decode（逐 token 生成），因为两者的计算特征不同。

### KV Cache

Key/Value Cache 缓存历史 token 在注意力层计算得到的 Key/Value 张量，避免每生成一个 token 都重新计算整个前缀。其优势是减少重复计算；代价是缓存随层数、上下文长度、并发请求和每 token 表示宽度增长，常成为显存容量瓶颈。缩短上下文、量化缓存和更好的内存管理解决的是不同问题。

### PagedAttention

通过固定大小的 KV blocks 将逻辑序列映射到非连续的物理缓存块，减少连续显存分配带来的碎片和预留浪费。块分配还便于请求扩展和释放。它优化的是缓存管理与并发容量，不会自动减少模型每层的注意力算量，也不能单凭这一设计断言任何工作负载上都更快。

### Continuous Batching

持续批处理允许新请求在运行中加入，并在请求结束后释放其位置，而不是等待整批最长请求全部完成。它能减少因输出长度差异造成的 GPU 空转，但调度策略可能影响尾延迟、公平性和长请求体验。比较时应同时报告吞吐、P50/P95 延迟、并发与请求长度分布。

### Prefill 与 Decode

Prefill 一次处理输入 prompt，通常适合并行矩阵计算；decode 则每步生成少量 token，常受到显存带宽、KV Cache 访问和小批次效率影响。只测单一阶段可能误判服务瓶颈；首 token 延迟、后续 token 速度和总完成时间应分别记录。

### TTFT（Time to First Token，首 token 延迟）

从请求被提交到第一个输出 token 可见的时间。它受排队、路由、模型加载、prefill、采样和网络传输影响。TTFT 低不等于后续生成快；应与 inter-token latency、端到端完成时间和吞吐一起看。

### 量化

把权重、激活或缓存从高精度表示为较低位宽或更紧凑格式，以降低内存和带宽需求。收益依赖量化算法、校准数据、硬件内核和模型结构；质量损失可能集中在某类任务或长上下文上。必须区分权重量化、激活量化和 KV Cache 量化，也要区分“内存更小”与“实际推理更快”。

### 低比特推理

在较低位宽下实际执行模型计算。位宽下降不保证延迟按比例下降：若硬件缺少对应内核、运算被反量化开销抵消或瓶颈在访存与调度，速度收益可能有限。评估需记录精度格式、算子实现、硬件、吞吐及输出质量。

### GGUF

常用于 llama.cpp 生态的模型文件格式，能够承载模型权重、量化类型和元信息。格式可读取只是必要条件：架构是否受支持、量化实现、后端算子与硬件是否匹配，都会影响加载与性能。不要把“模型转为 GGUF”视为无损或必然加速。

### Tokenizer

将原始文本映射到 token ID，再将模型输出 token 解码为文本。tokenizer 会影响序列长度、特殊 token、工具协议和上下文窗口占用；同一段文本在不同 tokenizer 下 token 数不同。因此比较模型上下文长度或吞吐时，必须说明具体 tokenizer 和输入 token 分布。

### 结构化生成

通过 JSON Schema、语法约束或有限状态机制限制模型可生成的字符串集合，减少格式错误。它能约束语法/结构，不自动保证数值合理、字段语义正确或事实真实。应把结构验证与业务校验、权限校验分开。

### 前缀缓存

复用相同或相似前缀的 prefill 计算结果，尤其适用于长系统提示和重复上下文。命中条件取决于 token 化结果、模型版本、缓存键和并行设置；缓存还需要内存预算及隔离策略。它不同于 KV Cache 的一般用途：KV Cache 保存单个进行中序列的历史状态，前缀缓存强调跨请求复用。

### 模型网关

位于业务应用与多个模型服务/供应方之间，处理路由、重试、限流、认证、成本统计、脱敏和负载均衡。统一 API 降低接入成本，但模型能力、上下文窗口、工具格式和安全策略仍不等价。自动重试要考虑重复扣费、重复执行和请求是否幂等。

### GGML / 本地推理后端

本地后端将模型权重映射到 CPU、GPU 或专用加速器执行。后端兼容性、算子覆盖、内存布局和数据搬运共同决定性能；在本地跑通示例不代表满足生产并发或交互延迟。

### 性能评测口径

至少记录模型与量化版本、硬件、软件版本、输入 token 数、输出 token 数、并发、TTFT、inter-token latency、总吞吐、峰值显存和输出质量。报告最大吞吐时要说明负载与统计方式；不同请求长度分布下的数字不能直接横向比较。

## 阅读建议

研究推理优化时按“瓶颈定位 → 单项机制 → 相同负载对照 → 质量回归”进行。避免把论文峰值吞吐直接外推到业务平均成本；用真实请求长度和并发分布重复测量。
