# Agent 与软件工程词典

Agent 系统把概率性的模型决策放进确定性软件环境中。理解其可靠性，需要分别检查任务状态、工具执行权限、结果验证、错误恢复和可观测性，而不能只观察最终文本是否通顺。

### Agent

能够根据目标和当前状态选择下一步动作、调用工具并利用结果继续执行的软件系统。Agent 不必然是多模型或自主系统；它可以是带循环的单模型加工具。关键属性是行动、反馈和状态变化。是否有效要看任务成功率、动作正确性、成本及失败恢复。

### 工具调用

模型输出一个结构化的工具请求，但**实际调用应由宿主程序完成**。执行前需要验证 schema、权限、资源范围、超时及副作用；返回结果也需被标记来源并重新加入上下文。模型提出调用不代表调用成功，更不代表结果可信。

### Handoff（控制权交接）

把任务从当前 Agent/节点交给专门执行单元，通常需传递任务目标、已有证据、剩余预算和返回方式。若上下文不完整会造成重复工作；若责任边界不清会出现多个 Agent 反复转交。应定义交接条件、终止条件和失败回退。

### 状态图

用节点表达步骤、用边表达条件跳转，适合有分支、循环、人工审批和失败恢复的工作流。显式状态有利于测试与审计，但状态 schema 设计不当会增加维护成本。应保证状态转换可观察、节点可单测，并明确哪些步骤具有不可逆副作用。

### Checkpoint（检查点）

保存工作流的状态、进度和必要上下文，以便中断后恢复。恢复需要同时处理外部系统是否已经完成动作的问题：若执行邮件发送后进程崩溃，直接重跑可能重复发送。Checkpoint 不是数据库事务；必须设计幂等键、动作记录和恢复前核验。

### 幂等性

对同一业务操作重复提交，不会额外产生副作用，或会返回同一操作结果。它是重试和断点恢复的关键基础。邮件发送、扣款、删除和部署等操作通常不能仅依赖“模型记住做过了”，而应由服务端使用请求 ID、幂等键或状态查询防止重复执行。

### 记忆

为未来任务选择性保存历史信息。常见实现包括摘要记忆、结构化事实、向量检索和外部知识库；它们的写入、遗忘和更新语义不同。记忆可减少重复交代，但也可能保存错误、过期或敏感内容，因此需要来源、时间戳、置信度、删除和冲突解决机制。

### RAG（Retrieval-Augmented Generation，检索增强生成）

先依据问题从文档或索引中取回相关片段，再把证据提供给模型生成答案。系统质量由切分、索引、查询改写、召回、排序、上下文窗口和生成共同决定。检索到材料不等于材料可信；还应检查引用是否支持断言，以及检索权限是否符合用户授权。

### Skill

把任务指引、资源、脚本或示例封装为可发现和复用的模块。Skill 能降低提示词重复并沉淀团队流程，但内容可能过期、触发不当或包含危险命令。技能本身不是隔离环境；脚本仍需审查，执行权限应由宿主系统控制。

### Tracing

记录一次任务中的模型调用、工具输入输出、耗时、异常和状态转换，帮助定位故障发生在哪个阶段。好的 trace 能把父子调用关联起来并跟踪重试；但记录过多 prompt 或工具返回可能泄露隐私。需要采样、脱敏、访问控制和保留期管理。

### Guardrail

对输入、动作、工具权限、输出或流程设置限制。关键安全边界应在确定性代码或外部授权系统中执行，而不是只要求模型遵守提示。Guardrail 仍可能误拦截或漏检，应通过红队样例、绕过测试和日志复核持续验证。

### 沙箱

将工具运行在受限环境中，隔离文件系统、网络、凭证、CPU/内存和执行时间。它降低工具被提示注入或恶意输入滥用的风险，但若挂载了高权限目录、继承环境凭证或允许任意出网，隔离就可能失效。权限应按任务最小化。

### 多 Agent 协作

多个执行单元分工完成一个任务。分工可能提高并行度或专业化，但会增加通信成本、共享状态冲突、协调延迟和错误传播。是否优于单 Agent 应通过相同任务集、预算与工具权限进行对照，不应根据角色数量判断。

### Agent 评测

评估整个执行链，而不仅仅是最终文本。至少记录任务完成率、工具选择/参数正确率、人工介入率、无效循环、重复副作用、成本、延迟和失败可解释性。测试任务应包含正常样本、边界条件、权限绕过和工具失败；只跑成功 demo 无法估计真实可靠性。

## 阅读建议

把系统拆成“模型建议—宿主校验—工具执行—结果验证—状态更新”。模型生成属于概率层，权限、幂等、文件/网络隔离和交易状态必须由可测试的执行层兜底。
