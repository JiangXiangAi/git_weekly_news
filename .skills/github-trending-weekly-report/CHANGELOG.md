# 周报 Skill 调整记录

## 2026-10-14 · v1.0

### 问题 1：Markdown 粗体标记可能出现字面量或渲染异常
- **经验：** 单看提交是否成功无法判断 Markdown 是否正确渲染；粗体嵌套在链接或整句高亮里，容易造成视觉不一致。
- **规则：** 每个项目技术分析先清理旧粗体标记，再高亮 1–2 个完整句子；禁止转义粗体标记、不匹配和嵌套粗体。
- **验证：** 扫描源文本中的转义星号；逐块检查技术分析的粗体标记；确认无临时标题“技术分析（约 300 字）”。

### 问题 2：六份方向报告的结构曾经不一致
- **经验：** 不同报告中出现不同的一级/二级章节名，会让读者难以比较。
- **规则：** 六份方向报告统一为“一、整体结论”“二、本周焦点”“三、Top 10 项目技术分析”三个二级章节。
- **验证：** 每份报告检查二级标题精确为三个，项目数和 Mermaid 图数都为 10。

### 问题 3：本周焦点容易退化成长期方法论
- **经验：** “关注技术趋势”“热度与质量要分开”等通用原则不能代替本周事实。
- **规则：** 本周焦点需有日期、具体项目事件和原始来源，解释变化机制及证据边界；无重要发布时可用真实 commit/PR，但标明它属于工程维护。
- **验证：** 检查第二章的日期、release/commit/PR/论文链接和分析是否直接基于来源。

### 问题 4：项目技术分析混入阅读教程
- **经验：** “如何读懂本项目”不是项目本身的技术判断，会稀释对机制和取舍的分析。
- **规则：** 删除阅读路线型章节，项目结尾写“技术判断与边界”；源码链接作为证据嵌入分析。
- **验证：** 搜索“如何读懂本项目”“阅读路线”“源码阅读路径”等旧模板。

### 问题 5：架构图比例和层级不一致
- **经验：** 横向图、节点标签过长和不同布局设置造成阅读体验不统一。
- **规则：** 每个项目单独一张纵向 Mermaid 图，统一 useMaxWidth、字体、节点间距、层间距和曲线配置。
- **验证：** 每份方向报告应有 10 张图，均使用 flowchart TD 和相同 init 设置。


## 2026-10-14 · v1.1

### 问题 6：部分项目分析的高亮过密，个别小标题带有临时字数说明
- **经验：** 即使单独看每一对粗体符号看似成对，过多句子加粗或在已有强调中再包一层强调，仍可能导致 Markdown 渲染不统一。
- **规则：** 六份报告的所有项目分析统一使用“技术分析”标题；每段先清除旧强调，再只保留 1–2 句关键机制/边界高亮，不做嵌套强调。
- **验证：** 六份报告重新读取后，确认每项分析最多两对粗体标记、没有反斜杠转义的星号、每份恰好 10 张项目图。
- **新增沉淀：** 本目录的 `SKILL.md` 成为后续每周生成的规范来源；未来如有用户调整，先改 Skill 与调整记录，再同步自动化任务。
