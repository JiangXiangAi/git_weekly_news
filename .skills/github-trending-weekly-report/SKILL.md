# GitHub Trending 技术周报 Skill

**规则版本：** 1.0  
**适用仓库：** JiangXiangAi/git_weekly_news  
**适用内容：** 1 份综合报告、6 份方向报告，以及本目录的规则维护。

## 1. 固定交付结构

每期只有 **1 份综合行业洞察 + 6 份方向报告**，方向为 LLM/大模型、AI Agent、自动驾驶、具身智能/机器人/世界模型、AI 与数学研究、Other。所有报告使用 Markdown，不生成 PDF；不要额外生成项目手册或泛化学习路线。

六份方向报告必须严格采用三个二级章节，标题固定如下：

1. `## 一、整体结论`
   用 1–2 段概括本方向本周最重要的技术判断，必须有周内事实依据，不写泛化口号。
2. `## 二、本周焦点`
   选 1–3 个与报告日期直接相关的具体事件、release、commit、PR、论文或研究材料。写明日期与原始来源，解释机制、实际影响和证据边界。本周若没有重大官方发布，可用有日期的维护记录；必须标记它是代码维护，而不是算法突破。
3. `## 三、Top 10 项目技术分析`
   每份方向报告精选 10 个项目，每个项目一个三级标题、一段技术分析、一张项目自己的 Mermaid 结构图，以及针对项目本身的“技术判断与边界”。不得另加第四个二级章节。

综合报告的结论先行也必须报告**本周具体发现**：推荐 3–6 个有日期、有来源的技术发现，解释为什么重要。通用统计口径、方法论和限制放在后续章节；“需要验证”“热度与质量不同”等常年原则不能冒充本周新闻。

## 2. 项目技术分析标准

每个项目的分析目标是帮助技术读者理解项目是什么、解决哪个真实瓶颈，以及它的机制为何可能有效，而不是提供简短新闻摘要。正文通常至少约 300 个中文字；复杂项目可以更长。

每个项目尽可能说清：

- **问题与背景：** 原有方法在哪个具体环节受限，问题来自算力、内存、数据、接口、泛化、控制、验证还是部署成本。
- **核心机制：** 项目采用了什么架构、算法、模型、数据结构、优化目标或运行时机制；数据/控制如何流经模块。
- **技术因果链：** 为什么该设计可能改善瓶颈，收益依赖哪些前提，付出了哪些延迟、内存、复杂度、可靠性或可维护性代价。
- **证据质量：** 链接到官方实现、论文、文档、release、commit、测试、benchmark 或 issue/PR。区分官方声明、项目方实验、独立复现、数学形式化检查和本报告推断。未找到支持某个性能主张的证据时，明确写出证据缺口，不补造数字。
- **边界与影响：** 说明剩余失败模式、与替代路线的差异、可能受影响的工程/研究环节以及判断成立的条件。

每个项目以“技术判断与边界”结束，突出实际价值、未解决问题与证据范围。

**禁止以下写法：** “如何读懂本项目”“阅读路线”“阅读时应”“源码阅读路径”等教读者怎样阅读的段落。源码和论文链接可以直接放在技术分析中作为证据，但不能用阅读教程替代技术理解和判断。

## 3. 本周焦点的选取规则

1. 日期必须处于报告周期内，标清时区或日期口径。
2. 优先使用官方 release、commit、PR、论文和公告。第三方周报或 Star 趋势可作发现线索，但要明确标注第三方来源。
3. 分开写发布事实、项目方对效果的声明、独立验证和分析推断。例如“提交修复了随机种子”可以由 commit 证明；“因此感知准确率提高”则需要另有实验依据。
4. 项目维护不是算法突破，但可以有技术意义：解释它如何影响可重复性、数据契约、故障隔离、依赖兼容或部署。
5. 无同口径周初/周末 Star 快照时，不给出精确周增和跨期排名。
6. 对重大科学主张要列出具体问题/猜想及原始材料。AI 数学报告尤其要区分自然语言证明、形式化 statement、内核检查、独立审查和同行评议，并追踪撤回/修订。

## 4. 项目级结构图：60 张独立图，统一样式

每个项目都必须有自己的一张图，描绘该项目内部架构、模块关系、输入输出、数据流、控制循环或研究工件/证据流。不能拿行业通用流程图替代项目图，也不能让十个项目共享一张总图。

统一规范：

- 使用 Mermaid `flowchart TD` 纵向布局。
- 每张图使用同样的 init 配置：`useMaxWidth: true`、`fontSize: 12px`、`nodeSpacing: 20`、`rankSpacing: 24`、`curve: linear`。
- 节点数建议 5–10 个，标签尽量简短；过长说明写到正文，避免宽度和高度不均。
- 根据官方 README、论文、文档或可见源码绘制。无法确认的内部机制写“待源码核验”，不凭空补全。
- 研究档案、数据集或工具项目没有传统模型架构时，画它自身的数据转换、训练/评测、状态或证据流，不能硬套神经网络图。

## 5. 关键术语与外链

不创建本地 glossary/ 词典。首次出现的重要专有名词，可用标准 Markdown 链接直达 Google 技术解释搜索，并在链接的 title 属性写一句可独立理解的中文释义。例如：

`[PagedAttention](https://www.google.com/search?q=PagedAttention+KV+Cache+explained "PagedAttention：以固定大小块管理 KV Cache，减少连续显存分配约束")`

要求：

- title 是有技术含义的中文提示，不只是重复英文词。
- Google 搜索链接用于术语学习或延伸解释；支持关键事实的引用仍应优先指向官方源码、论文、文档、release 或 benchmark。
- 外链文本与链接 URL 应保持有效；Markdown title 引号须闭合。
- 不依赖 JavaScript 或专用网页组件来实现悬停提示。

## 6. Markdown 粗体与源文本检查

用户曾反馈 Markdown 粗体标记有时以转义文本显示，且技术分析过度/嵌套加粗会造成渲染不统一。为防止重复发生：

1. 直接检查实际文件源文本，不只看生成器回报。
2. 不能在 Markdown 正文中留下带反斜杠转义的粗体标记；如需显示星号字符，应使用代码样式，不能混入正文。
3. 技术分析通常只加粗 **1–2 个完整句子**，优先突出核心机制和重要边界。不要把一个已有粗体短语再包进整句粗体，避免嵌套和相邻的四星标记。
4. `**技术分析**` 的小标题统一，不加“约 300 字”等临时注释。
5. 不要把整段背景都加粗；关键术语用外链提示，关键机制/结论用少量粗体。
6. 写入前对每个技术分析块清除旧粗体标记，再按句子重新选择高亮；检查粗体标记成对、无不匹配或嵌套。
7. 每份方向报告应只有三个二级章节、10 个项目三级标题、10 个 Mermaid 图；每张图都是纵向并使用一致 init 配置。
8. 扫描 `技术分析（约 300 字）`、`阅读路线`、`如何读懂本项目` 等旧模板是否残留。
9. 检查 Google 术语链接与直接来源链接是否仍有效、路径是否指向旧 glossary。
10. 更新后重新 fetch 文件验证提交版本；若样式存在疑问，再抽查原始 Markdown 片段，不能把“提交成功”等同于显示正确。

## 7. 综合报告写作规则

总报告应从六个方向中抽取可比较的技术变化，解释架构范式、资源瓶颈、验证方式和系统边界如何变化。避免仅罗列项目，也不要把方向报告直接拷贝成表格。每条结论尽量形成“本周事实 → 技术机制 → 对工程/研究的意义 → 证据边界”的链路。

## 8. 交付前检查清单

- [ ] 1 份综合报告 + 6 份方向报告，没有额外 PDF 或项目手册。
- [ ] 六份方向报告的二级章节标题完全一致且只有三个。
- [ ] 每个方向都精确有 10 个项目、10 张独立结构图。
- [ ] 本周焦点有日期和直接来源，并区分维护、发布和效果主张。
- [ ] 每项技术分析有实质机制、取舍、证据和失败边界，不只是功能摘要。
- [ ] 没有“如何读懂项目/阅读路线”教程段落。
- [ ] 技术分析的标题统一为 `**技术分析**`。
- [ ] 不遗留转义的粗体标记；粗体标记配对正确，无嵌套或过量高亮。
- [ ] 图全部纵向，使用相同尺寸配置，标签不过长。
- [ ] 关键术语用 Google 搜索解释 + title 释义；关键事实链接官方原始材料。
- [ ] 总报告结论先行是本周具体发现，不是通用方法论。
- [ ] 文件提交后重新读取并核验关键规则。

## 9. 规则演进

遇到新问题时，把它写入同目录 `CHANGELOG.md`，至少说明：发现的问题、修订后的规则、采用原因和验证方法。改动核心格式或每周自动化 prompt 后，必须同步更新本 Skill，避免规范分叉。
