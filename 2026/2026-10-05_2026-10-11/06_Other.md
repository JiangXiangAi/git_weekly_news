# 方向报告 06｜Other：数据、评测与开发者基础设施

**周期：** 2026-10-05—2026-10-11  
**定位：** 收纳不直接属于五个主方向、但会影响 AI 工程落地的通用基础设施。它不是“其他热门项目”的随意列表。

## 本期判断

模型和 Agent 的能力需要数据治理、评测、追踪、部署与开发工具支撑。这些项目通常不直接创造新模型能力，却决定研究结果能否被复现、部署和维护。以下为长期工程入口，不是本周官方 Trending 排名。

## 10 个项目精读

### 1. [MLflow](https://github.com/mlflow/mlflow) — 实验、模型与评测追踪
**背景/方法：** 参数、数据版本和指标常散落在脚本或笔记中；MLflow 记录实验参数、指标、工件与模型版本。  
**解决的问题：** 建立可追溯实验记录，比较不同配置并复现实验。  
**影响判断：** AI 系统越复杂，实验谱系越是研发资产。  
**阅读路线：** Tracking API → 实验/运行数据模型 → artifact 存储 → 模型注册 → 权限和部署边界。

### 2. [Weights & Biases](https://github.com/wandb/wandb) — 训练与实验可观测性
**背景/方法：** 分布式训练和大量对照实验难以仅靠日志文件追踪；SDK 记录训练指标、配置、工件和可视化信息。  
**解决的问题：** 提升实验对比与协作能力。  
**影响判断：** 实验可观测性影响团队迭代速度，但需管理数据上传和敏感信息。  
**阅读路线：** run 生命周期 → 配置/指标记录 → artifact 版本 → 离线/在线模式 → 数据隐私策略。

### 3. [Evidently](https://github.com/evidentlyai/evidently) — 数据与模型质量监控
**背景/方法：** 线上数据分布变化会让离线表现无法代表真实环境；Evidently 提供数据质量、漂移和模型表现报告。  
**解决的问题：** 把数据变化转成可观察信号，辅助定位模型退化。  
**影响判断：** 部署后的持续评测与上线前评测同样重要。  
**阅读路线：** 数据 schema → 漂移计算 → 报告生成 → 阈值与告警 → 误报与基线选择。

### 4. [Ragas](https://github.com/explodinggradients/ragas) — RAG 系统评测
**背景/方法：** 检索增强生成可能流畅却无依据或漏掉关键资料；Ragas 围绕上下文、答案相关性和忠实性等维度设计评测。  
**解决的问题：** 把检索与生成问题拆成可测量的部分。  
**影响判断：** 自动评审能辅助迭代，但评审模型自身也有偏差。  
**阅读路线：** 指标定义 → 样本与参考答案 → judge 模型调用 → 与人工标注对照 → 指标稳定性。

### 5. [DeepEval](https://github.com/confident-ai/deepeval) — LLM 应用回归测试
**背景/方法：** Prompt、模型或检索配置变化会引起语义回退，普通单元测试难以覆盖；DeepEval 提供 LLM 应用测试用例和指标接口。  
**解决的问题：** 将部分语义质量检查纳入开发与 CI。  
**影响判断：** LLM 应用会逐渐采用回归测试，但测试集覆盖决定门禁是否有效。  
**阅读路线：** test case schema → 指标实现 → judge 模型与阈值 → CI 集成 → 失败样例和误报/漏报。

### 6. [OpenTelemetry Python](https://github.com/open-telemetry/opentelemetry-python) — 跨服务追踪标准
**背景/方法：** Agent 调用模型、检索、数据库和工具时，单一日志难定位延迟；OpenTelemetry 以 traces、spans、metrics 描述调用链。  
**解决的问题：** 追踪跨服务调用和性能瓶颈。  
**影响判断：** Agent 需要统一观测标准，才能比较成本、延迟和失败位置。  
**阅读路线：** span 生命周期 → context propagation → exporter → 敏感属性过滤 → 多服务调用链追踪。

### 7. [DVC](https://github.com/iterative/dvc) — 数据与模型工件版本化
**背景/方法：** Git 不擅长直接追踪大型数据集和模型文件；DVC 将数据/工件与 Git 元数据关联，并管理流水线。  
**解决的问题：** 把数据版本纳入实验复现链。  
**影响判断：** 数据谱系是 AI 研究可复现性的关键组成。  
**阅读路线：** 元数据文件 → remote 和缓存 → pipeline → 版本切换 → 验证同一输入能否复现。

### 8. [Great Expectations](https://github.com/great-expectations/great_expectations) — 数据契约与质量检查
**背景/方法：** 数据缺失、类型变化和业务规则漂移会在训练或推理中引入错误；项目把数据预期写成可执行检查。  
**解决的问题：** 在数据进入下游前发现结构和质量异常。  
**影响判断：** 数据质量约束能减少把输入问题误诊为模型问题。  
**阅读路线：** expectation 定义 → 验证执行器 → 失败结果 → pipeline 集成 → 异常样本测试。

### 9. [BentoML](https://github.com/bentoml/BentoML) — 模型打包与服务化
**背景/方法：** 训练环境中的模型不容易直接成为有版本、依赖和接口约束的生产服务；BentoML 把模型与服务逻辑打包。  
**解决的问题：** 降低从实验到服务的工程转换成本。  
**影响判断：** 模型部署会越来越需要版本、健康检查和回滚机制。  
**阅读路线：** service 定义 → 模型工件 → 打包/容器构建 → 请求处理 → 部署与回滚。

### 10. [Ray](https://github.com/ray-project/ray) — 分布式 Python 计算
**背景/方法：** 数据处理、搜索、训练和推理需要跨进程或多机扩展；Ray 用 task、actor 和资源调度抽象分布式执行。  
**解决的问题：** 让 Python 工作负载更容易扩展到多核和多机。  
**影响判断：** 分布式抽象能降低工程门槛，但不会自动消除通信开销、数据倾斜和故障恢复问题。  
**阅读路线：** task/actor API → 资源调度 → 数据传递 → 失败恢复 → 单机与多机基准比较。

## 方法论沉淀

基础设施的价值在于把实验、数据和线上行为连接起来。优先确认是否有可追溯版本、固定基线、失败样例、权限控制和可复现运行命令。评测术语见[研究证据词典](../../glossary/evaluation.md)。
