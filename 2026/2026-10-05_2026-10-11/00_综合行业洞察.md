# 开源科技与数学研究｜综合行业洞察

**统计周期：** 2026-10-05—2026-10-11　**整理日期：** 2026-10-13

## 结论先行

1. **竞争焦点从模型单点能力转向“生成—执行—验证”的完整系统。** LLM 服务需要控制显存、请求调度和延迟；Agent 需要明确状态、工具权限和恢复；机器人需要把策略输出变成物理动作并处理反馈；AI 数学则要把自然语言主张变成可审查、可形式化的证明工件。它们共同面对的不是让输出更流畅，而是让输出在真实约束下产生可检查的结果。
2. **系统瓶颈往往出现在模块交界处。** 推理服务的瓶颈可能从 attention 算量转移到 KV Cache 容量、访存和排队；Agent 的错误可能发生在工具 schema、外部副作用和 checkpoint 恢复之间；驾驶与机器人常被时间戳、坐标系、控制频率和分布偏移限制；形式化数学则容易在自然语言主张与形式化 statement 的映射上出现缺口。读项目应沿数据流定位接口，不应只按模型名称分类。
3. **AI 数学带来了较强的科研工作流信号，但不是“结果目录即定理库”。** [OpenAI/math](https://github.com/openai/math) 的公开 README 列出 722 篇手稿、372 个结果家族；材料涉及**准黎曼假设、Hilbert 第十问题在有理数域上的版本、Unique Games 猜想和 Seymour 第二邻域猜想**等主题。官方仓库也注明并非所有结果均已完成 [Lean 形式化](https://www.google.com/search?q=Lean+proof+assistant+kernel+checking "Lean：依赖类型论证明助手，内核检查形式化证明项")，修订记录中有撤回和更正。**模型产出候选论证、数学家独立审查和形式化内核通过是不同证据层级**；其潜在冲击是降低候选探索成本，同时把筛选、查错和验证推到更重要的位置。[结果概览](https://github.com/openai/math/blob/main/overview.tex) · [修订历史](https://github.com/openai/math/blob/main/history.md)
4. **机器人/驾驶应从离线分数走向闭环因果链。** 数据集与仿真工具让实验更可重复，但离线检测或轨迹误差不能回答动作是否安全。只有在固定场景中观察策略动作改变未来状态、错误如何累积、失败能否恢复，才能更接近系统级能力判断；而仿真结论还需明确到硬件、ODD 和真实环境的迁移证据。
5. **评测与可观测基础设施不是外围工具，而是研究可信度的一部分。** 实验谱系、数据版本、线上 tracing 和自动回归评测决定工程团队是否能定位退化与复现结果。仪表盘或 CI 绿灯本身不是正确性证据，关键是记录能否关联到代码、模型、数据、运行条件和失败样例。
6. **热度证据与技术判断必须分开。** 本期是首期归档，尚无自有同口径周初/周末 Star 快照。方向报告将“本周趋势线索”和“长期研究/工程入口”分开呈现，不虚构周增排名，不把项目方声明改写成独立验证。

## 跨领域技术结论

### 1. 将概率性决策与确定性验证分层

模型负责生成候选、预测或动作，但外部约束最好由可测试的执行代码、物理环境、形式系统或业务规则检查。LLM 的 schema 校验不保证语义正确；Agent 的工具请求需经过权限检查；机器人动作需要控制和碰撞边界；数学证明需要对形式化命题执行内核检查。这种分层减少了“让模型自己承诺正确”的单点信任问题，但并不能消除错误建模。

### 2. 接口契约是隐性错误的主要来源之一

在 LLM 中，tokenizer、上下文长度、缓存键和流式协议影响服务行为；在 Agent 中，工具输入输出、状态 schema 与 checkpoint 决定能否恢复；机器人系统依赖时间戳、坐标系、动作单位和控制频率；数学形式化依赖类型、隐含假设和 import。**接口能连通不代表语义已对齐**。因此每个项目分析都应把入口、数据结构、模块交界、测试和失败路径一起读。

### 3. 评测需要匹配实际主张

- **性能主张**：固定模型/版本、硬件、输入长度、并发和统计方法，并同时报告质量、延迟和内存。
- **Agent 能力主张**：任务成功率之外，还需要工具误用、人工介入、重复副作用、成本和恢复效果。
- **机器人/驾驶主张**：绑定 ODD、任务定义、本体、场景和控制条件；分离开环指标、闭环仿真与真实硬件结果。
- **数学主张**：逐一检查原始命题、假设、推理和引用；区分自然语言论证、计算实验、形式化证明与同行审查。

### 4. 从“可演示”到“可维护”的分水岭是证据链

一次成功 demo 通常只覆盖一条路径。更可靠的工程系统应保留版本化输入、可复现运行命令、评测基线、失败样本、修订历史和回滚机制。**好的基础设施不是让结果看起来更可信，而是降低第三方检查和反驳它的成本。**

## 本期持续观察

1. OpenAI/math 后续的撤回/修订、独立评议和 Lean 形式化覆盖情况。
2. Agent 框架在固定任务集上能否同时提高成功率并降低人工返工、重复副作用和成本。
3. 推理运行时在同一模型/硬件/负载下的质量—吞吐—尾延迟—显存权衡。
4. VLA 与机器人策略在留出本体、扰动场景和真实硬件中的失败恢复能力。
5. 自动驾驶项目从离线评测到闭环仿真/受控道路的证据覆盖。
6. 同一项目池建立连续 Star 快照，但把热度变化与技术价值分开解释。
