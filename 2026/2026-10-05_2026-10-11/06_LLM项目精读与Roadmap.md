# LLM 与大模型｜项目精读手册与 Roadmap

> 这是研究与实践路线，不是热度排名。具体安装方式、支持硬件、维护状态与许可会变化，复现前请以官方 README、Release、License 和 issue 为准。本期没有同口径 Star 快照，不猜测周增量。

## 一、先建立全景图

把 LLM 系统拆成五层：模型与算法；模型接口与网关；推理运行时；部署与资源；评测与监控。学习顺序是先调通 API，再搭模型网关，然后运行本地模型，最后比较高吞吐推理服务和量化方案。每次实验固定模型、硬件、输入长度、输出长度和并发度。

## 二、10 个项目精读卡片

### 1. [BerriAI/litellm](https://github.com/BerriAI/litellm) — 模型网关
**问题与价值：** 业务应用接入多家模型时，需要统一路由、重试、限流、日志和成本核算。网关把这些横切逻辑从业务代码中分离。
**精读什么：** Provider adapter、请求/响应标准化、fallback、预算/限流、异常映射、日志脱敏。
**实战：** 接入两个模型，模拟超时与限流，验证 fallback、重试次数和计费；检查日志是否暴露 prompt 或密钥。
**验收：** 成功率、P95 延迟、fallback 成功率、每任务成本、重试放大率。
**注意：** 重试可能重复产生副作用或费用；统一接口不代表不同模型语义完全一致。

### 2. [microsoft/BitNet](https://github.com/microsoft/BitNet) — 低比特推理
**问题与价值：** 降低模型权重的内存和计算成本，使模型更容易在资源受限硬件上运行。
**精读什么：** 量化表示、推理内核、硬件指令依赖、权重转换流程，以及官方 benchmark 的模型与基线。
**实战：** 固定任务，对比基准配置与低比特配置的内存、tokens/s、首 token 延迟和质量。
**验收：** 峰值内存、吞吐、质量退化、支持上下文长度。
**注意：** 论文或 README 的数字不能外推到所有硬件；量化格式和内核实现会影响结果。

### 3. [lyogavin/airllm](https://github.com/lyogavin/airllm) — 低资源推理
**问题与价值：** 显存不足时，分层加载或卸载可降低 GPU 峰值内存，但通常增加延迟。
**精读什么：** 权重分片、加载顺序、CPU RAM/磁盘/GPU 数据搬运、缓存策略与并发限制。
**实战：** 从小模型逐步增大规模，记录峰值显存、主存、磁盘读取和每 token 延迟。
**验收：** 能否启动、内存峰值、首 token 与每 token 延迟、稳定性。
**注意：** 能加载不代表可交互使用；磁盘带宽和上下文长度可能成为瓶颈。

### 4. [vllm-project/vllm](https://github.com/vllm-project/vllm) — 高吞吐推理
**问题与价值：** 多用户请求会造成 GPU 利用率低、显存浪费与排队延迟；KV cache 管理和 continuous batching 是核心研究点。
**精读什么：** PagedAttention/KV cache、请求调度、并行策略、兼容 API 与服务指标。
**实战：** 用同一模型改变并发度、输入长度和输出长度，比较单请求速度与总吞吐。
**验收：** 总 tokens/s、请求吞吐、P95 延迟、OOM 比例、GPU 利用率。
**注意：** 总吞吐提高可能伴随单请求延迟上升；长上下文改变缓存压力。

### 5. [huggingface/text-generation-inference](https://github.com/huggingface/text-generation-inference) — 模型服务
**问题与价值：** 模型服务需要加载、批处理、流式响应、健康检查、监控与硬件适配。
**精读什么：** 容器启动、模型分片、健康检查、指标端点、流式返回、版本兼容。
**实战：** 部署一个模型，加入并发压测、重启恢复和健康检查；与其他推理服务做同负载对照。
**验收：** 启动时间、可用率、吞吐、P95、升级与回滚难度。
**注意：** 先核实项目当前维护状态与模型支持范围，不要只沿用旧教程。

### 6. [ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp) — 本地/边缘推理
**问题与价值：** 在不依赖云 API 的情况下运行模型，覆盖 CPU、GPU 和边缘设备。
**精读什么：** GGUF 格式、量化级别、后端抽象、采样参数、KV cache 和构建选项。
**实战：** 同设备对比两种量化级别，固定 prompt 集，记录质量、内存、速度和可测功耗。
**验收：** 内存、tokens/s、模型质量、部署体积和可运行性。
**注意：** 模型文件大小不是唯一指标；后端与编译参数影响性能。

### 7. [ollama/ollama](https://github.com/ollama/ollama) — 本地模型管理
**问题与价值：** 降低模型下载、运行与本地 API 集成的门槛。
**精读什么：** 模型清单与模板、API、模型存储、并发行为和服务暴露方式。
**实战：** 从命令行运行模型，再用 Python 客户端调用；检查服务绑定地址和资源占用。
**验收：** 首次启动体验、重复调用延迟、资源使用和客户端集成难度。
**注意：** 本地运行不自动等于安全；避免把无认证服务暴露到公网。

### 8. [huggingface/transformers](https://github.com/huggingface/transformers) — 模型开发生态
**问题与价值：** 统一 tokenizer、模型加载、训练与推理接口。
**精读什么：** AutoTokenizer/AutoModel、配置、权重加载、生成参数、pipeline 与底层调用差异。
**实战：** 手工完成 tokenizer→模型→生成流程，再改变采样参数、上下文和 batch。
**验收：** 实验可复现、加载成功、显存估算和输出质量记录。
**注意：** 模型代码、权重和 tokenizer 版本要匹配；默认参数可能隐藏关键行为。

### 9. [sgl-project/sglang](https://github.com/sgl-project/sglang) — 结构化生成运行时
**问题与价值：** 复杂生成需要约束输出、复用前缀和调度请求，而不只是逐 token 生成。
**精读什么：** 结构化输出、前缀缓存、调度机制、服务协议及与其他运行时的比较方法。
**实战：** 构造 JSON 输出和共享长前缀请求，测结构合法率、吞吐、缓存命中与 P95。
**验收：** 输出合法率、吞吐、延迟、显存和稳定性。
**注意：** 不同 benchmark 的 prompt 和输出长度不同，不能直接横比。

### 10. [openai/openai-python](https://github.com/openai/openai-python) — API 客户端可靠性
**问题与价值：** 生产客户端必须处理认证、超时、流式响应、重试和类型化结果。
**精读什么：** 客户端配置、异常分类、自动重试、流式事件、异步调用与类型定义。
**实战：** 写一个客户端，测试超时、限流、断流、无效参数与取消请求。
**验收：** 错误分类、超时退出、重试次数和流式中断行为。
**注意：** 不要提交密钥；日志需要避免暴露敏感输入。

## 三、6 周 Roadmap

| 周次 | 学习主题 | 交付成果 |
|---|---|---|
| 1 | tokenizer、生成参数、SDK | 固定测试集与可重复推理脚本 |
| 2 | 网关、路由、限流、成本 | 双模型网关，含 fallback 与脱敏日志 |
| 3 | 本地推理与量化 | llama.cpp/Ollama 对照实验 |
| 4 | vLLM/SGLang 与 batching | 并发压测，报告 P50/P95、tokens/s |
| 5 | 低比特/低显存策略 | 内存、延迟、质量对照表 |
| 6 | 稳定性与复现 | 环境锁定、回归脚本、技术决策记录 |

## 四、毕业项目：LLM Serving Lab

搭建统一测试台，比较本地运行时、推理服务和模型网关。固定模型、硬件、输入数据、量化和请求分布；保存 commit、配置、环境、原始日志和失败样例。

**最终交付：** 可运行代码、架构图、质量/吞吐/延迟/成本表、部署说明和已知限制。没有原始日志和复现步骤的性能结论不算完成。

## 五、精读顺序
Transformers → OpenAI SDK → LiteLLM → llama.cpp/Ollama → vLLM/SGLang → BitNet/AirLLM → TGI。先理解模型调用，再理解接入、部署和性能优化。
