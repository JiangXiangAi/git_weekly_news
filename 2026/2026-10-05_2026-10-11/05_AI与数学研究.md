# 方向报告 05｜AI 与数学研究：候选发现、证明工件与形式化可信边界

**周期：** 2026-10-05—2026-10-11

## 本期焦点：OpenAI/math 与研究工件化

[OpenAI/math 官方仓库](https://github.com/openai/math)公开了一批由内部模型生成的数学手稿与支持性证明材料。当前 README 列出的规模为 **722 篇手稿、372 个结果家族**；项目方还描述了约 4,000 个问题经过模型处理和筛选聚合的工作流。此处数字属于项目方披露，并非独立算力审计，也不能将手稿数量直接视为已获数学共同体确认的新定理。

公开目录列出的具体研究主题包括**准黎曼假设（Quasi-Riemann Hypothesis）**、**Hilbert 第十问题在有理数域上的版本**、**Unique Games 猜想与近似阈值**、**Seymour 第二邻域猜想**，以及 Kaplansky 特征二直接有限性猜想、Mahler 猜想的相关形式等。它们触及数论、可计算性、组合优化与代数等不同分支，而非单纯提升竞赛题得分。需要强调：仓库给出的是研究主张、手稿和证明材料，并不是本报告独立验证后的结论。官方记录显示，并非每项结果都已完成 [Lean 形式化](../../glossary/math.md#lean "Lean：基于依赖类型理论的证明助手，可由内核检查形式化证明")，历史中也出现过因符号错误影响论证而撤回、修订的手稿。**正确性必须逐项核查假设、推导、文献优先权、独立复现和形式化覆盖率**。[结果概览](https://github.com/openai/math/blob/main/overview.tex) · [修订历史](https://github.com/openai/math/blob/main/history.md)

这可能改变数学研究流程：当模型能批量产生候选证明和关联线索，研究者的时间可能从从零草拟转向筛选、查错、校对假设和建立可信证明。它的潜在冲击不是“模型替代数学家”这么简单，而是**候选生成成本下降之后，验证和品控可能成为新的瓶颈**。但只有经过独立审查、可靠形式化或同行评议的结果，才能逐渐进入稳定数学知识体系。

## 10 个项目/研究入口精读

### 1. [OpenAI/math](https://github.com/openai/math) — 把 AI 产出的数学主张组织为可修订档案

**技术分析**

传统数学论文通常以整理后的证明和叙述为主，研究者难以观察一次大规模 AI 探索中产生了哪些候选结果、相关推论或替代论证。**OpenAI/math 将手稿按[结果家族](../../glossary/math.md "结果家族：同一主张及关联推论、替代证明或补充材料")组织，并保留可更新的材料与历史记录，使研究者能从一个主张追踪到相关证明与修订。**其研究流程可理解为：模型对问题提出候选结果与论证草稿，筛选/整理形成结果家族，再由数学家检查定义、隐含假设、关键引理和已有文献。需要特别区分**生成和归档机制**与**数学正确性**：目录能展示研究产量，不能证明每份手稿正确、原创或达到同行审查标准。最有效的阅读单位不是整份目录，而是一个具体结果：先把主定理写成精确命题，再核对每条假设、引用、引理依赖和证明中未展开的步骤；之后检查是否有形式化工件及历史修订。官方历史中存在撤回/修订，说明对这类系统而言，错误追踪也是研究基础设施的一部分。

**项目结构图**

```mermaid
flowchart TD
  A[开放数学问题/提示] --> B[内部模型产生候选结果]
  B --> C[问题筛选与材料整理]
  C --> D[结果家族：主张/推论/替代证明]
  D --> E[数学家检查假设与推导]
  E --> F{可信度状态}
  F -->|待形式化| G[补充 Lean/其他验证工件]
  F -->|有疑点| H[修订/撤回/保留争议]
  G --> I[独立审查/同行评议]
  H --> I
  I --> J[更新后的公开档案]
```

**如何读懂本项目：** 从 README 的生成流程说明开始，打开 [overview.tex](https://github.com/openai/math/blob/main/overview.tex) 选一个具体结果；逐项列出前提、主命题、关键引理与引用，再对照 [history.md](https://github.com/openai/math/blob/main/history.md) 检查更正记录。没有形式化证明时，不将结果标为已由内核验证。

### 2. [Lean 4](https://github.com/leanprover/lean4) — 让证明对象经过可信内核检查

**技术分析**

自然语言证明可能省略中间推导，审阅者需凭数学训练判断是否存在漏洞。**Lean 把命题编码为类型，把证明编码成满足该类型的项；tactic 可以自动化构造[证明项](../../glossary/math.md "证明项：在形式系统中对应命题类型的证明对象")，但最终要由内核按形式规则检查。****搜索器或语言模型可以复杂甚至不完全可信，内核检查是缩小信任边界的关键**。不过，内核只能判断形式化后的命题是否被证明，不能保证形式化命题准确表达研究者原本想说的数学结论；错误定义、错误假设或不恰当的建模仍可能产生“形式上正确、数学上答非所问”的证明。因此读 AI 生成的 Lean 结果时，要先审 statement 的量词、域、边界条件和隐含类型类假设，再看 theorem 的证明项是否真正闭合、是否留下未完成占位。内核通过是强证据，但仍需把形式化陈述与自然语言主张对应起来，并检查依赖库的公理与假设。

**项目结构图**

```mermaid
flowchart LR
  A[数学命题/定义] --> B[Lean 类型化 Statement]
  B --> C[Tactic/自动化搜索]
  C --> D[证明项 Term]
  D --> E[Kernel 类型检查]
  E -->|通过| F[该形式命题的证明已检查]
  E -->|失败| G[修复策略/命题/证明]
  F --> H[人工核对形式化与原始数学主张]
```

**如何读懂本项目：** 从一个基础 theorem 开始，观察 tactic 如何生成 term；再看 kernel 相关代码和测试，区分 tactic 的搜索职责与 kernel 的检查职责。对 AI 生成证明，检查是否存在未解决目标、额外公理及 statement 偏差。

### 3. [Mathlib](https://github.com/leanprover-community/mathlib4) — 把可复用数学知识变成形式化依赖图

**技术分析**

形式化一道复杂定理的成本不仅来自最后几行证明，还来自先前定义、局部引理、代数结构和数论/分析基础必须先编码。**Mathlib 通过社区积累的定义、定理和证明，把这些知识变成可 import、可类型检查的依赖库。**它让研究者把工作建立在已有 lemma 上，也为自动化证明提供可检索的形式化知识；另一方面，库的命名空间、[类型类](../../glossary/math.md "类型类：在 Lean 中表达需满足的结构/实例约束，影响定理适用条件")实例和依赖版本会显著影响证明脚本。对自动证明而言，知识库不是普通全文搜索：一个定理是否可用取决于其准确类型、参数、隐含实例和当前 import 环境。数学家应检查所引用定理是否真正满足需要，而不能只因名字相似就认为适用。大型形式化项目还需留意 build 时间、依赖变更和 API 稳定性。**Mathlib 降低重复形式化成本，但不会替代对问题建模与命题正确性的判断**；基础库越成熟，验证流程越可扩展，也越需要良好的依赖管理。

**项目结构图**

```mermaid
flowchart TD
  A[Definitions / Structures] --> B[基础 Lemmas]
  B --> C[高层 Theorems]
  C --> D[其他文件 Import]
  E[类型类/实例解析] --> C
  F[定理检索与复用] --> C
  C --> G[Lean Kernel 检查]
  G --> H[CI/版本构建]
```

**如何读懂本项目：** 选一个与目标问题相关的 theorem，先看类型签名和命名空间，再沿 lemma/import 依赖往下追；检查实例解析、使用的公理及 CI 测试，而不止复制证明代码。

### 4. [AlphaGeometry](https://github.com/google-deepmind/alphageometry) — 神经候选扩展与符号几何推理

**技术分析**

几何证明包含大量辅助点和中间关系，纯符号搜索可能在组合爆炸中耗费大量时间；单纯神经网络生成步骤又难保证几何约束与推理规则正确。**AlphaGeometry 采用神经语言模型提出辅助构造/候选步骤，再把候选送入[符号推理系统](../../glossary/math.md "符号推理系统：按明确规则推导关系，可检查候选步骤")检查和扩展，利用两种方法互补：模型扩大搜索方向，符号系统负责满足形式规则。**它不是直接从像素中理解任意几何图，而是在结构化几何表示和给定规则体系中搜索证明路径，因此结论适用范围受表示语言、可用构造和数据分布限制。阅读时应区分模型提供的启发式优先级与符号引擎确认的推理步骤，理解搜索何时分支、何时剪枝，以及停止条件如何定义。其代表性意义是展示**神经方法可负责提出候选，确定性推理器负责约束验证**，但不等于证明了同样架构能直接推广到所有数学分支。

**项目结构图**

```mermaid
flowchart TD
  A[结构化几何问题] --> B[几何符号状态]
  B --> C[符号引擎现有可推导关系]
  B --> D[神经模型建议辅助构造/候选步骤]
  D --> E[候选加入搜索队列]
  C --> F[规则推导/状态扩展]
  E --> F
  F --> G{目标定理是否可推出}
  G -->|否| H[继续搜索/回溯]
  H --> C
  G -->|是| I[输出证明链并检查]
```

**如何读懂本项目：** 先看论文中的双系统流程和几何表示，再追踪候选构造如何进入符号引擎；选一个公开几何题，标记每步来自模型建议还是形式规则推导，并检查搜索失败条件。

### 5. [SymPy](https://github.com/sympy/sympy) — 精确符号表示与代数运算

**技术分析**

数学探索经常需要化简表达式、分解多项式、求解方程或检查特例。**使用浮点数可能引入舍入误差，也可能掩盖表达式结构；SymPy 将数学对象表示成[表达式树](../../glossary/math.md "表达式树：以节点结构表示数学表达式，便于精确重写")，在其上运行重写规则和特定符号算法。**表达式树让运算的结构可追踪，但不同形式的表达式未必都能通过通用 simplify 得到唯一“最简”结果；某些积分或方程也不存在简单闭式解。因此要区分精确符号变换、数值近似和启发式化简，明确算法的适用域及返回结果的条件。SymPy 可用于生成猜想线索、检查低维特例和构造反例候选，却不能因为有限个样例成立就证明一般命题。尤其是除法、根式、分支切割和参数约束，默认假设可能影响等价变换。读源码时应从表达式节点进入具体算法模块，追踪分支条件并以独立恒等式或数值检查验证输出。

**项目结构图**

```mermaid
flowchart LR
  A[输入表达式/方程] --> B[SymPy Expr Tree]
  B --> C[表达式规范化/模式匹配]
  C --> D{操作类型}
  D --> E[化简/重写]
  D --> F[因式分解/多项式算法]
  D --> G[求解/积分/极限]
  E --> H[符号结果]
  F --> H
  G --> H
  H --> I[假设核对/独立验证]
```

**如何读懂本项目：** 从一个 Expr 的构造和 args 树结构开始，追到 simplify、factor 或 solve 的目标模块，核对参数假设和测试；用符号代回、边界值和独立数值计算验证结果。

### 6. [SageMath](https://github.com/sagemath/sage) — 将多个数学计算系统组合成实验平台

**技术分析**

研究者常需在数论、代数、组合和几何等领域切换不同的成熟系统；分别安装、调用并交换数据会增加环境和接口成本。**SageMath 通过统一的 Python 环境和对象层连接多个数学库/工具，让同一实验能组合[精确代数计算](../../glossary/math.md "精确代数计算：以符号/精确对象运算，区别于近似浮点计算")、数值计算与专门算法。**这个集成层的意义是减少脚手架成本，而不是让所有底层工具拥有相同语义或可信等级：某些操作精确计算，另一些依赖浮点近似；外部软件还可能具有不同许可、编译或版本要求。计算实验适合发现规律、检验有限参数范围和寻找反例，但“对大量样例算出来都成立”仍不等于普遍定理。阅读时要追踪某个 Sage 对象究竟调用哪一个后端，确认数据类型、精度和算法默认值，再决定结果能支持哪一级主张。对于 AI 辅助数学，SageMath 更适合充当探索和计算验证层，而非自动提供形式化证明的替代品。

**项目结构图**

```mermaid
flowchart TD
  A[Python/Sage 用户表达式] --> B[Sage 数学对象层]
  B --> C[类型/算法分派]
  C --> D[数论与代数后端]
  C --> E[组合/图论后端]
  C --> F[数值/符号外部工具]
  D --> G[结果标准化/转换]
  E --> G
  F --> G
  G --> H[实验表格/候选模式]
  H --> I[证明/形式化工具进一步验证]
```

**如何读懂本项目：** 选择一个数论或代数操作，追踪 Sage 接口到实际后端，检查输入类型、精度和底层算法；再测试边界参数并区分精确结果与数值近似。

### 7. [Open-R1](https://github.com/huggingface/open-r1) — 开放推理模型的训练与评测管线

**技术分析**

推理模型性能不仅由基础模型决定，也依赖问题分布、答案[验证器](../../glossary/math.md "验证器：按规则检查答案/证明/输出，能力受其支持范围限制")、奖励设计、采样温度和训练预算。**Open-R1 的工程价值在于将数学/推理数据、训练配置、评测及可复现脚本开放出来，便于研究者检查从样本到优化目标的流程。**若采用可验证奖励，正确答案或工具检查结果可作为监督信号，但验证器覆盖不到的解法、格式变化和多答案等情况会带来奖励偏差。若评测题目泄漏进训练集，benchmark 分数也可能高估泛化。阅读时应从数据过滤和去重一路追到 reward 计算、采样策略、优化器配置与评测调用，核对生成结果如何转换为 reward，以及训练与测试是否真正隔离。**数学推理任务分数提高不等价于模型已发现新数学定理**；要评价研究能力，还需考察新问题、长证明、反例构造、证明检验和专业审查表现。

**项目结构图**

```mermaid
flowchart TD
  A[原始推理/数学数据] --> B[清洗/去重/切分]
  B --> C[Prompt 与采样]
  C --> D[模型生成解答/推理轨迹]
  D --> E[Verifier / Reward 计算]
  E --> F[策略优化/训练更新]
  F --> C
  G[独立评测集] --> H[评测脚本与基线比较]
  F --> H
  H --> I[泛化与污染审查]
```

**如何读懂本项目：** 先运行一个官方评测，再沿数据处理脚本追踪过滤规则，找出 reward/verifier 的实际判定条件；对照训练配置记录采样、预算和基线，重点检查测试题泄漏及指标覆盖盲点。

### 8. [Numina](https://github.com/project-numina/numina) — 数学问题与推理轨迹的数据资源

**技术分析**

数学模型训练的数据质量不仅取决于题目数量，还取决于来源、解答正确性、推导完整度、难度分布、授权情况和与评测集的重合。**Numina 提供数学推理相关数据资源和使用入口，其价值是让训练管线能以统一 schema 消费题目与解答，再进行清洗、混合、采样和训练。**但大规模数据集中常有重复题、不同表达的近重复题、错误解答、无效格式或超出许可范围的材料。若只统计总行数，无法判断数据的真实有效覆盖；随机切分还可能把相同题目的改写分配到训练与测试两边。应构建数据审计：检查题源与许可证、解析失败率、[去重](../../glossary/math.md "去重：识别相同和近重复样本，防止切分泄漏与虚高指标")粒度、答案一致性和难度分布，并把数据版本与模型 checkpoint 关联。数据集可扩大模型接触的题型，但其本身不证明模型掌握了数学概念，更不证明推导可被验证。

**项目结构图**

```mermaid
flowchart LR
  A[多来源题目/解答] --> B[格式解析与 Schema 统一]
  B --> C[来源/许可/语言筛查]
  C --> D[精确/近重复去重]
  D --> E[答案与推导质量检查]
  E --> F[难度/题型统计与采样]
  F --> G[训练数据版本]
  G --> H[模型训练]
  I[留出评测集] --> J[污染/相似题检查]
  G --> J
```

**如何读懂本项目：** 从数据 schema 和来源信息开始，抽样检查题目、答案与推导；运行精确及近重复检测，统计解析失败、题型与难度，再确认训练集与评测集隔离方式。

### 9. [LeanProject](https://github.com/leanprover-community/LeanProject) — 用 Blueprint 维护论文与形式化代码的映射

**技术分析**

大型形式化工作常涉及数百个定义、引理和主定理；如果代码中的 theorem 与自然语言论文段落没有稳定映射，团队很难知道哪些论证已完成、哪些依赖仍缺失。**LeanProject/Blueprint 这类工具把论文结构、定理节点、[依赖关系](../../glossary/math.md "依赖关系：主定理、引理和定义之间的结构化依赖链")和 Lean 代码位置联系起来，形成可导航的证明工程图。**它主要改善项目管理、可追溯性和协作，并不自动证明蓝图里的每条陈述；只有实际形式化的 statement 与证明通过内核检查，才构成相应形式证据。维护者仍需保证自然语言段落、图节点和代码中的命题一致，且依赖图在代码重构后更新。对于 AI 生成的长证明，蓝图可帮助把主结论拆成可检查子目标，追踪哪些引理由机器证明、哪些仍待人工填充。要阅读时应选一篇示例论文，从主定理沿依赖图下钻，并核实每个节点的 Lean 源码和构建状态。

**项目结构图**

```mermaid
flowchart TD
  A[论文自然语言章节/主定理] --> B[Blueprint 定理节点]
  B --> C[引理依赖图]
  C --> D[Lean 文件/namespace/theorem]
  D --> E[编译与 Kernel Check]
  E --> F{完成状态}
  F -->|已证明| G[蓝图节点标记完成]
  F -->|缺失/失败| H[待办引理/编译错误]
  G --> I[论文与形式化覆盖审计]
  H --> C
```

**如何读懂本项目：** 打开一个有 blueprint 的仓库，把自然语言主定理对应到节点，再沿依赖链接定位 Lean 声明；检查构建状态、占位证明和命题表述是否匹配论文。

### 10. [Lean Community](https://github.com/leanprover-community) — 将形式化证明纳入可审查的软件协作

**技术分析**

大规模形式化数学库不能只靠个人脚本维护：依赖升级可能让证明失效，命名风格会影响搜索，未完成证明和隐含公理也可能影响可信度。Lean community 是多个社区形式化项目的协作入口，而不是单一算法仓库；它展示的工程机制包括贡献指南、代码审查、固定工具链、自动构建和依赖版本管理。AI 生成的证明若想变成可维护的公共知识，必须遵守同样的标准：代码可读、依赖可追踪、构建可复现、证明无未完成占位，并且命题与论文主张一致。**[CI](../../glossary/math.md "CI：持续集成，自动运行构建、测试与证明检查") 通过只能说明在当前固定环境中代码通过检查，不能保证数学陈述的建模没有错误，也不能证明原创性或优先权。**社区审查和版本控制是长期可信度的补充层。阅读时不要只看组织页，要进入具体项目的贡献规范与 PR，观察修改如何经过编译、审查和依赖升级。

**项目结构图**

```mermaid
flowchart LR
  A[贡献者/AI 生成的 Lean 补丁] --> B[格式/命名/依赖检查]
  B --> C[PR 人工审查]
  C --> D[固定工具链构建]
  D --> E[Kernel 检查与测试]
  E --> F{审查结论}
  F -->|通过| G[合并与版本发布]
  F -->|失败| H[修订/补证明/调整声明]
  H --> B
  G --> I[下游项目锁定依赖版本]
```

**如何读懂本项目：** 从具体仓库的贡献指南和 CI 配置入手，追踪一个 theorem 修改的 PR，查看工具链版本、构建错误与 review 讨论；区别代码合并、内核通过和数学共同体接受三个状态。

## 方法论沉淀

- 将**模型提出主张、自然语言证明审查、形式化 statement、内核检查、独立复现和同行评议**视为不同证据状态。
- 检查假设是否完整、引用是否正确、未证明引理是否被隐藏，以及形式化命题是否覆盖主结论。
- 记录撤回与修订。对 AI 数学系统而言，发现错误后能定位、修正和防止复发，是可靠研究流程的重要组成。
